# Architecture audit

## Current implementation

Traffic includes a Python desktop app and a React browser dashboard. `main.py` launches either a CustomTkinter dashboard or a command-line A/B benchmark. `api.py` serves typed FastAPI state and WebSocket updates to `web/`, whose React/Three.js interface renders live SUMO vehicle and signal state over a procedural intersection. `backend/simulation.py` manages SUMO through TraCI and owns the fixed-time and adaptive controllers. `backend/data_loader.py` generates SUMO network and demand files. `backend/optimizer.py` provides constrained green-time allocation, `numerical_methods.py` contains numerical routines, and `metrics.py` records and exports telemetry. The desktop dashboard is split across `frontend/app.py`, `dashboard.py`, and `charts.py`.

The simulation state is SUMO-driven. Fixed/adaptive comparisons use paired labeled SUMO sessions and update both chart streams live. The browser scene draws a procedural city/intersection and instanced vehicles from actual SUMO positions; its geometry and buildings are illustrative, not imported from a surveyed city model. The browser also exposes live metrics, decision events, detector flow equations and row operations, completed-run summaries, CSV/JSON telemetry exports, and quality controls. Recording/replay is not implemented. No `reference/` directory or reference images were found in the project.

## Decorative, not simulated

- Procedural buildings, trees, sidewalks, road surface treatment, lighting, and other static props are scenery only. They do not appear in SUMO state, controller inputs, telemetry, or performance metrics.
- The intersection layout is an illustrative visualization of the SUMO network, not a surveyed geographic model. Its decorative geometry must not be interpreted as map coordinates or live road-condition data.
- Every moving vehicle rendered by the browser must come from the live SUMO vehicle list and use its reported position, heading, speed, lane, and vType. Decorative parked vehicles are not currently present.
- The current project does not render pedestrians. If pedestrians are added, each one must be backed by a real SUMO person object and remain absent when no such object exists.
- Weather, ambient effects, and time-of-day changes (if added) are cosmetic controls, explicitly labeled as such; they must not modify measured simulation results.

## Data and safety flow

Scenario, configured demand, and seed are passed to `SumoNetworkBuilder`, which writes the SUMO network and route inputs. SUMO advances the vehicle state. The runner samples halting counts, induction-loop counts, and vehicle telemetry, calls the selected controller, and sends recorded telemetry to the UI callback and CSV exporter. The adaptive controller uses measured queue counts and Gauss–Jordan checked detector flow estimates in the constrained optimizer; it uses configured demand only before its first detector interval. Both controllers use SUMO's configured traffic-light phase sequence, with yellow and all-red clearance phases between the two green movements.
